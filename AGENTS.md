# project-kit

This repo is the kit itself. **Read this routing rule before anything else.**

- **Asked to bootstrap or set up a project at another path?** Follow
  [Bootstrapping another project](#bootstrapping-another-project). Change nothing in
  this repo, and ignore the `## Work protocol` at the bottom — that governs work on
  the kit, not work on the project you were asked about. You do not need to be in
  this directory at all: `kit` is on `$PATH`.
- **Asked to change the kit?** See [Changing the kit](#changing-the-kit), and run
  `kit next` here for the current plan.

## Bootstrapping another project

```sh
kit init /path/to/project              # docs only
kit init /path/to/project --stack go   # also Makefile, go.mod, cmd/, CI
```

**Never delete or clear the target directory first.** `kit init` creates what is
missing and never overwrites or removes anything, so it is safe to run on a
directory that already has files, on a populated repo, and repeatedly. Emptying a
target to "start clean" destroys work and is never required.

It creates the directory if needed, makes it a git repo, and writes the docs. Use
`--stack` when the language is known; it is what gives the project a working
`make check`. Do not scaffold deployment (terraform, ansible, images) at init —
that waits until there is something to deploy.

Then work **inside the new project**, not here:

1. Run `kit new "<what the feature does>"` inside the new project — it writes the
   doc with the next free ID and today's date. Fill in Problem, Non-goals, Design,
   and Tasks. Never copy the template by hand.
2. `## Tasks` boxes are PR-sized outcomes, in the order they should be done. If you
   cannot say how you would verify a box is done, it is too big — split it.
3. Anything you cannot decide goes in `## Open questions`; leave `status: Draft`
   until those are settled. Anything only the human can decide goes in
   `docs/INBOX.md` with your leaning.
4. Set `status: Accepted` once the design is settled, then run
   `kit next /path/to/project` to confirm it hands back the first task.

Never invent product decisions on the human's behalf. Ask in `docs/INBOX.md`.

## Changing the kit

```sh
make check     # fmt-check, vet, unit tests, conformance suite
make install   # go install ./cmd/kit
```

**Run `make install` after anything lands on `main`.** `kit` on `$PATH` is one
binary shared by every project, so a merged change reaches none of them until it is
reinstalled. This is not housekeeping: the first real project built with the kit ran
against a binary two features behind, so it was scaffolded without `docs/VISION.md`,
got a protocol with no rule about drafting from one, and never ran the secret check.
Nothing reported anything wrong, because from inside that project nothing was.

`make check` is the whole gate. The conformance suite lives in `cmd/kit` as
`conformance*_test.go`: it builds the binary once and drives it against throwaway
projects, so `init`, `next`, and `audit` are covered as a user runs them. It is a Go
test on purpose — the previous suite was an external script outside the build, which
is how it got deleted without anything noticing.

Note that `cmd/kit` coverage reads low and will stay there. The conformance tests
drive a subprocess, so nothing they exercise is instrumented; the number is not a
signal for this package.

If you add a check to `audit`, add a test that it fires and a test that it stays
quiet, and document the code in README.md. `TestEveryRegisteredCheckIsExercised`
enforces the first half — a check with no conformance case fails the build.

Two layout constraints that are easy to trip over:

- Files under `templates/` must not be valid Go package files or a nested module —
  `go vet ./...` would try to compile them. That is why the templates are named
  `gomod`, `gitignore`, and `main.go.tmpl`.
- Templates are embedded via `assets.go` at the repo root, because `go:embed`
  cannot reach a parent directory from `cmd/kit/`.

## Work protocol

Run `kit next` at the start of every session. It names the feature and the task.
Run `kit audit` when you want to know what has drifted. `kit help` explains the
whole model, and `kit help template` prints the feature doc format.

### Picking and finishing work

1. **Asked to plan something? Read `docs/VISION.md`, then draft — all of it.**
   It says what the project is for and what it is not; a feature that cannot be
   traced to it is the wrong feature, and saying so is cheaper than building it.
   Bootstrapping a project means producing the **whole set** of features it needs,
   not the first one. Do not wait to be asked to decompose.

   **Split by the vision's `## What done looks like`.** Each observable outcome there
   is at least one feature; that list is where the boundaries come from.

   **A feature is one pull request** — you push a branch and a human reads it, so the
   feature is the unit of review. Too big is a PR nobody can review in one sitting:
   config, storage, the API and the CLI together is a project, not a feature. Too
   small is one that changes nothing anyone can observe and exists only so the next
   can start — that is a task box, not a doc.

   **Say what each one waits on in `needs:`**, and fill it in for every draft: it is
   what lets `kit next` refuse work whose foundation is missing, and several features
   with an empty `needs:` is what lets agents run at once. Judge it by whether the
   work could *start* now — a shared composition root, a shared router, or numbered
   files in one sequence such as migrations all make a feature dependent however
   separate it looks.

   **Leave every doc `Draft`: accepting is a human's call.** A draft waits on a
   branch of its own — nothing is ever committed to
   `main` — and **that branch is deleted when the draft is accepted and merged**. Its
   name is the claim name, so leaving it behind makes the feature unclaimable: every
   agent is then told it is taken, by nobody.
2. **One agent per feature. Take it with `kit claim <id>`.** That pushes the branch
   named after the doc, and creating that ref on the remote is what decides who
   gets the work: exit 0 is yours, exit 1 means another agent got there first — run
   `kit next` and take something else. Losing is normal and costs nothing. Never
   create the claim branch by hand: a branch only you can see is not a claim, and a
   push that reports "up to date" found somebody else's.

   **A feature `kit next` lists as taken is not yours.** Not to work on, not to tick
   a box in, not to "help with" because it looked slow. One agent per feature means
   one, and two agents in one feature produce one branch nobody can review.

   **If nothing is free, stop.** Everything claimed or waiting is a real answer and
   the right one — say so and wait for a human. Do not pick up claimed work, do not
   start a feature nobody accepted, and do not invent something to be useful. An
   idle agent costs nothing; two agents in one feature costs the feature.
3. **One feature per checkout. Work in the worktree `kit claim` prints.** The
   worktree is the isolation and git provides it; the kit only refuses to hand out
   work in a checkout that is occupied. Run in one, `kit next` reports that feature
   as *yours* and will not offer you another to start — starting a second one where
   you stand puts two features in one branch and they ship as one.
4. **Read the feature doc for the design.** Never restate or re-derive design
   anywhere else.
5. **Do the topmost unticked `## Tasks` box, and only that one.** List order is the
   order of work. Tick it in the same commit that implements it — you do not open the
   PR, so the commit is the unit that has to be honest. Among features of equal
   status, `kit next` goes by ID, lowest first.
6. **Discovered work** becomes a new `## Tasks` box, a new feature doc
   (`kit new "<title>"`), or a line in `docs/features/BACKLOG.md` if it is real but
   not now. Never a `TODO` in the code. Append it unless it genuinely blocks the
   boxes below it — list order is priority, so appending is what says "later".
7. **A box that turns out wrong may be rewritten, split, or deleted** — in its own
   commit, with the reason in `## Log`. The plan is a working document; only
   `status: Shipped` freezes it. What you may not do is silently drop a box you
   could not finish.
8. **Stopping mid-feature? Release the claim.** Delete the branch locally *and* on
   the remote (`git push origin --delete <branch>`), set the status back to
   `Accepted`, and say why in `## Log`. The pushed branch is the claim, so deleting
   only your local copy leaves the feature taken for good and `kit next` will route
   every future agent around it.
9. **Blocked on a decision only a human can make?** Run
   `kit block <id> "<question, with your leaning>"`, then move to another feature.
   Do not guess. Use `--fyi` for anything work can continue without. "Do not idle"
   means do not sit on a question you could have filed — it is not licence to take
   work that is not yours; see **One agent per feature** for when stopping is correct.
10. **Never put a real secret in a doc.** Feature docs, `## Log`, and `docs/INBOX.md`
   are committed, and a pushed commit cannot be unpublished. Name the variable and
   where the value lives — never the value. `audit` reports `secret-in-doc` at HIGH
   for the shapes it can be certain about, which is a backstop and not the rule: a
   password in prose matches nothing and is still a leak.
11. **Never edit a doc with `status: Shipped`.** It is frozen history.
12. **When the last box is ticked, run `make check` and `kit audit --strict`, then
    `kit ship <id>`.** Those two are the gate: green means the code holds and the docs
    and the repo agree. `kit ship` verifies every box is ticked, sets the status and
    stamps the date — doing that by hand is where `unticked-shipped` and
    `shipped-no-date` come from, which is why the command exists. Then move durable
    facts into the as-built doc (`docs/TECH.md`).
13. **Shipping is a handoff, not a finish.** Push the branch and stop there.
    Reviewing and merging are not yours. If the project has no remote, the work
    has nowhere to go — say so and leave it on the branch rather than merging it
    yourself, which is how unreviewed work reaches `main` without anyone deciding
    it should.

### Where two agents can still collide

The claim is airtight and the ID is not. `kit new` takes the next free ID from what
it can see on disk and never goes to the network, so two agents drafting at once on
two branches can both produce `0009`. Nothing in git objects: the filenames differ,
so the merge is clean.

`kit audit` reports it as `duplicate-id`, and it is HIGH because the ID is the
primary key — one branch would claim both features and one INBOX line would block
both. `kit claim` refuses an ID that two docs share for the same reason.

Fix it before claiming either: give one doc a free ID, rename its file to match, and
rename its branch if it already has one. Run `kit audit` after any merge that brought
in feature docs written elsewhere.

### Doing the work

The rules above decide *what* to work on. These govern *how*, and bias toward caution
over speed on anything non-trivial. Use judgement on trivial tasks.

- **Think before coding.** State assumptions out loud. Where a request is ambiguous,
  name the readings rather than silently picking one. Push back when a simpler
  approach exists, and stop when confused — say what is unclear instead of guessing
  past it. **Blocked on a decision only a human can make** is where a question goes
  when only a human can settle it.
- **Simplicity first.** The minimum code that solves the problem. Nothing
  speculative, no features beyond the box you are on, no abstraction for a single
  use. If a senior engineer would call it overcomplicated, it is.
- **Surgical changes.** Touch only what the task requires. Do not improve adjacent
  code, comments, or formatting, and do not refactor what is not broken — match the
  style already there. Clean up your own mess and nobody else's. Unrelated problems
  you spot are **Discovered work**'s business, not this change's.
- **Define success, then loop.** Say what "done" looks like before starting, and
  verify it yourself rather than reporting completion and hoping. A box you cannot
  check the truth of was too big; split it.
