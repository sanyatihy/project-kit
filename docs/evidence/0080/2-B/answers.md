# Answers

1. **No.** Exit 1 is a completed negative result: another agent's claim exists, and a claimed branch or worktree belonging to another agent is not yours to clean up. Deleting its branch by hand would destroy the winner's claim; kit only permits cleanup of an unchanged, unoccupied losing attempt after a confirmed competing winner, and never tells a losing claimant to delete the winner's branch. Run `kit next` and choose different work.

2. **Keep the receipt and retry `kit claim` from that same clone when online.** An unknown push outcome retains evidence in `refs/kit/claims/<id>`; an interrupted claim is not a confirmed loss, so neither ownership nor its absence may be inferred. Retrying reconciles the unique empty receipt with the remote — claim 0 includes recovery of recorded ownership. Do not delete refs or hand-edit to "clear" it.

3. **No, the claim is not lost.** A worktree failure cannot undo a won claim: the branch acquisition succeeded. Preserve the obstructing files (kit preserves them; an existing matching worktree would be reused as success) and retry worktree creation. Do not delete the other agent's or your own obstructing files to force it through.

4. **Preserve the work, don't release it.** Release refuses unmerged commits, including doc-only changes — the commit is work, so `kit release` (even `--discard`) is the wrong tool for something you consider valuable. Commit and push the branch, open the pull request unfinished, and say what remains; the human can then decide whether to merge or fold it in. Do not silently delete the unmerged plan change.

5. **No.** An explicit offline audit covers local checks only and labels its reduced coverage (`offline: true`); offline evidence cannot certify remote ownership, publication or integration, and an unanswered remote is not evidence of absence. The online validation is incomplete — complete the strict online audit (fetching missing advertised objects) before handing off to review.

6. **No, do not reopen it.** A Submitted doc on trunk is frozen history; further changes need a new feature citing it by id instead of copying its reasoning. Draft a new feature for the operator's behavior change (human approval through merge before implementation). Reopen only applies to unmerged submissions and would be refused here.

7. **Work the independent, ready feature.** The blocking question stops `next` offering that one feature, but not all work: take independent work from another trunk checkout (one feature per checkout; claims are per-branch), or report the blocker and stop. Never invent a product decision to unblock the blocked feature — its answer goes in via `kit block`, recorded in the plan once the human answers.

8. **Run `kit init` in place without clearing anything.** Init exclusively creates missing files and never clears the target, so it is safe on a populated project: it refreshes only the real Work protocol section of AGENTS.md (between its markers), backfills id reservations and missing CI, and leaves everything else alone. Preserve the custom Makefile and CI — init does not update existing stack files, so compare them against current scaffolds yourself — and keep the house rules outside the Work protocol section so they survive the refresh. Never refresh a newer project protocol from an older binary.

9. **The identifier is defined in the check registry in `audit.go`** (`featureChecks`/`repoChecks`), with help generated from it; every registered check must have exactly one implementation and one conformance case, so adding the check means registering its id there plus implementing it and a test case — not prose. A prose rule is **not** sufficient to enforce human-only merge: agents can bypass kit with raw git, shared credentials defeat identity separation, and only remote merge permissions and required checks enforce who may merge. Prefer enforcement in the tool (or remote) over another protocol rule.

10. **Set `exec.Cmd.WaitDelay` within the 15-second remote-call budget** so a killed git command also reaps subprocess helpers still holding the output pipe — killing git alone can leave a helper alive, which is exactly what happened with the black-holed remote (75s until WaitDelay brought it to 15.05s). **No**: do not export `CGO_ENABLED=0` into race tests; the stripped build's environment must stay out of them, or the race detector cannot run.
